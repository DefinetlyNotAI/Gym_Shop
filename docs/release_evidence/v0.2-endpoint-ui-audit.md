# v0.2 endpoint-to-UI audit — 2026-09-12

Status: in progress. This is not a claim that every endpoint is reachable or that v0.2 is complete.

The inspected API has 136 `api/v1` route files and 169 exported HTTP method handlers, plus its public `/media/[id]` delivery route. Reachability must be assessed by method and real workflow, not just a matching URL string. A public read route can intentionally host a permission-protected write method: product creation uses `POST /api/v1/catalog/products`; the admin catalog listing uses `GET /api/v1/admin/catalog/products`.

## Completed catalog reachability slice

| API contract | Actual UI consumer |
| --- | --- |
| `GET /admin/catalog/products` | Staff Products, Categories, Collections, Size Guides workspaces, protected by `catalog.read` |
| `POST /catalog/products` | Products → Create product & initial SKU, default Draft; names, descriptions, price, stock and grouping/guide assignment |
| `PATCH /admin/catalog/products/[id]` | Product disclosure panels → content/pricing/groupings and variant price, barcode, weight, visibility/purchasability/tracking |
| `POST /admin/catalog/taxonomy` | Independent Categories and Collections creation forms |
| `POST /admin/catalog/size-guides` | Independent Size Guides → named size/measurement/value rows and units, no mandatory JSON editing |
| `POST /admin/catalog/media` | Product Gallery → own scan-ready image, bilingual alt text and ordering |
| `POST /media`, signed upload PUT, finalize POST | Shared staff upload control; double submission disabled, 10 MB limit, scan-pending state; scan completion is never a public approval button |
| `GET /catalog/products/[slug]`, public media delivery | Staff “View product” link → customer product detail, selectable gallery and readable size table |
| `GET /catalog/taxonomy/[kind]/[slug]` | Grouping “View customer page” links → customer category/collection pages |

All paths in the table except `/media/[id]` are relative to `/api/v1`.

Catalog safety corrections: bind inferred PostgreSQL arrays as one parameter (including empty tags); reject PDF/video, unscanned or another owner's upload for gallery publishing; do not return storage keys; retain inactive grouping choices and original primary-category order on unrelated saves. The primary category has an explicit choice. Customer media uses direct delivery for controlled redirect URLs; SIM media streams bytes through the same-origin route rather than redirecting to the API port and violating the existing resource policy.

## Remaining reachability candidates to implement and verify

The initial source inventory did not find normal workflow controls for the following methods. They remain open; a documentation row or generic “call API” button does not complete them:

- Customer `POST /support/claims`. Logout, cancellation and review reporting controls were added in the follow-up slice below; report-form runtime acceptance still needs a published-review fixture.
- Staff `POST /admin/support/claims/[id]/decision`, own-message `PATCH /admin/support/tickets/[publicId]/messages/[messageId]`, `POST /admin/inventory/returns/[orderId]`, `POST /admin/finance/discrepancies`, `POST /admin/notifications/templates`, driver `POST /deliveries/cash/handover`.
- Recovery `POST /recovery/resend`; read-only health/release readiness presentation and dedicated pickup/location configuration reachability outside the CTO launch page need review.
- `POST /account/payouts` and `POST /admin/finance/payouts/[id]/decision`: APS beneficiary-disbursement capability is unverified. Existing customer/staff pages must explain unavailable withdrawals, not create financial holds or pretend execution is enabled. Verified provider evidence is still required for R02-05/R02-08.

## Machine boundaries

Payment provider returns/webhooks are provider-facing flows consumed by hosted checkout and status reconciliation, not manual staff success toggles. `/jobs/outbox` is the authenticated scheduler's reconciliation/delivery boundary. `/media/scan-result` is the authenticated scanner's result boundary. SIM upload/object/payment/session/inbox endpoints are local-only test transport. They should have UI-visible outcomes and operational evidence, but must not be exposed as unsafe public controls. Setup and recovery WebAuthn endpoints require real physical-key proof; automated UI inspection does not certify hardware ceremonies.

## Evidence for this slice

Tests were written and observed failing before implementation: migrated product creation with empty tags failed at SQL; unsafe PDF gallery publication incorrectly succeeded; inactive groupings were missing; checkbox-order save changed the primary; simulated gallery delivery returned a cross-origin redirect. Corresponding regression journeys now cover the real migrated database, not source-string assertions. Client request tests execute the production request/form builders, covering methods/encoded IDs, null/removal semantics, primary ordering, guide rows, integer fils and upstream errors. Customer presentation tests execute the production size-table transform.

Browser acceptance in credential-free, memory-only SIM: create bilingual category/collection/size guide, create Draft product with stock and assignments, inspect persisted selections, publish product, save variant override/weight, search/filter, publish two owned synthetic scan-ready images, select the second customer image and inspect actual decoded image widths. Mobile 390×844 and English/Arabic/RTL layouts were inspected; no document horizontal overflow in tested views. Synthetic image bytes are fixtures, not marketing assets. Production R2 delivery and real APS payments/payouts are not certified by this local test.

Final verification for this slice: API suite 65 tests across 17 files; v0.2 software acceptance 30 tests across seven files and 98 migrated tables; admin request/routing suite 12 tests; customer presentation suite three tests. All three production builds and lint checks passed. The browser recheck decoded all three gallery images and showed M before L in the Arabic size table at 390 px without horizontal overflow. Software acceptance explicitly does not authorize APS wallet-withdrawal activation.

## Follow-up customer actions

- `/account` now has an explicit `POST /auth/logout` action. Browser acceptance confirmed session revocation and return to the sign-in form, with private account content removed.
- Order detail now exposes `POST /orders/[publicId]/cancel` only before packing, with required explicit consent and truthful, separate refund messaging. Browser acceptance confirmed required consent, cancellation state, and a refreshed cancellation timeline for an unpaid SIM order.
- Product reviews now expose `POST /reviews/[id]/report` with API-supported reasons and optional bounded details; helpful actions encode IDs and handle failures. The review layout, sorting labels and states are localized. Error handling preserves report form text rather than allowing React function-action form reset. Published-review success/error browser acceptance, including retained fields after a failed report, remains open.
- The real migrated v0.1 financial journey reproduced a cancellation retry failure. A locked, ownership-scoped early return now prevents repeated inventory/wallet/refund/event mutation and preserves an already-refunded payment state. The expanded API suite remains 65 passing tests; customer request/presentation tests now total six. API/customer builds and lint passed for this follow-up.
- Runtime issue discovered and still open: the browser-created SIM checkout order persisted, but the native simulated payment form received HTTP 403 and left checkout showing a placing-order state. This does not certify a completed simulated payment journey. Do not weaken trusted-origin protections to hide this failure.
