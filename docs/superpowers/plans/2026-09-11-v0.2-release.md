# Gym Shop v0.2 Release Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver and verify the complete R02-01 through R02-08 Gym Shop v0.2 release across the API, storefront, and staff applications while keeping provider-gated CliQ execution visibly unavailable.

**Architecture:** `api.example.com` remains the sole owner of PostgreSQL state, pricing, rewards, referrals, reviews, verification, payouts, subscriptions, and analytics. `example.com` and `admin.example.com` consume versioned API contracts and contain no business or database logic. Every scarce money, usage, weekly-reward, first-order, and payout transition is transactionally guarded and idempotent; domain events feed notifications without coupling messaging success to business commits.

**Tech Stack:** Next.js 16.3.4, React 19.2.8, TypeScript 5.9.3, PostgreSQL/Neon, PGlite acceptance tests, Vitest 5, Zod 4.

**Spec:** `../../../../PLAN/releases/v0.2.md` plus the linked pricing, wallet, referrals, identity, support/reviews, notifications, analytics, payments, defaults, architecture, decisions, and security contracts.

## Global Constraints

- Preserve `PLAN/` byte-for-byte and verify `git status --porcelain PLAN` remains empty at release closeout.
- Keep `example.com`, `api.example.com`, and `admin.example.com` independently deployable; only the API owns backend routes and domain/database services.
- JOD values use integer fils; points use integer milli-points so 1 point equals 1,000 milli-points.
- Business weeks begin Monday 00:00 in `Asia/Amman`; calculate boundaries server-side.
- Points and wallet balances never expire; reversals and holds are explicit ledger activity, never expiry.
- Wallet value is tender, not a discount, and has no checkout percentage or source restriction.
- Business CliQ execution remains unavailable unless a real contracted provider adapter, credentials, tariff, callback/status contract, and sandbox evidence are configured.
- Each API mutation requires trusted-origin validation, server authorization, stable error codes, idempotency where value can repeat, audit evidence, and domain-event emission.
- Existing v0.1 behavior and acceptance verification remain release prerequisites.
