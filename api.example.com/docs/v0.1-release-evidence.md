## Runtime journey

The browser-operated simulation created and paid a card order, packed it as CTO, dispatched it to the seeded driver, exposed the encrypted WhatsApp delivery PIN only in the signed-in customer's simulation inbox, accepted driver custody, and completed the attended delivery with that PIN. The final customer order view showed `COMPLETED · PAID · DELIVERED` and an immutable timeline containing creation, card confirmation, packing, dispatch, PIN and delivery events. The staff dashboard exposed separate CTO, admin and driver views; the driver view contained only the assigned shipment and was empty after completion. Separate API-driven simulator probes verified that `failure` produces `CANCELLED · FAILED · CANCELLED` with its reservation released, while `pending` remains `CREATED · PENDING · UNFULFILLED` for reconciliation.

## Production activation gates

Preview/production deliberately reject simulation mode and incomplete credentials. A live release still requires real Neon connectivity, Amazon Payment Services credentials and callback allow-listing, approved WhatsApp/email providers and templates, R2 credentials/scanning, production domains, and a human two-key recovery drill recorded through the readiness workflow. Those are deployment inputs and operator evidence, not missing v0.1 code paths.
